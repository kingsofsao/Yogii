# Model card: Yogii prototype risk model v1.0.0

> **Synthetic data only. Prototype thresholds. Not for real payments.**

## Overview

| | |
|---|---|
| Model | Three XGBoost binary classifiers (amount, behaviour, context), a rule-based payment graph and receiver-side score, and a linear-regression stacker |
| Version | 1.0.0 (`models/yogii_risk_model.json`) |
| Engine of the committed artifact | xgboost 3.2.0 (`hist`, single thread), exported to a browser tree format |
| Alternative engine | `ml/xgb_numpy.py`, a numpy implementation of the same algorithm |
| Output | A risk score from 0 to 100 and a band (LOW 0–29, MEDIUM 30–59, HIGH 60–84, VERY_HIGH 85–100) |
| Runs in | The browser (`src/app.js`), fully offline; Python port in `ml/check_scenarios.py` |

## Intended use

- Demonstrating how a pre-PIN risk check could explain itself to a payer inside a **simulated** payments app.
- Teaching and prototyping: features, anomaly components, graph signals, stacking and model-based limits.

## Out-of-scope use

- Any real payment, lending, KYC or account decision.
- Any claim about real-world fraud rates or detection performance.
- Labelling a person or account as fraudulent. Graph links are signals, never proof.

## Training data

- `data/synthetic_transactions.csv`, generated by `ml/synthetic.py` with seed 42: 24,000 rows over a fictional 180-day window. **No real people, accounts or transactions.**
- Features are drawn from hand-written distributions. They include a sender profile (average amount, balance, account age), spikes, bursts, new recipients, night-time payments and new devices.
- **Labels are synthetic:**
  - Each component has a hand-written "anomaly severity" in [0, 1]. The label is a Bernoulli draw from that severity.
  - The **analyst rating** is a weighted sum of the three severities, the graph score and the receiver score, plus Gaussian noise (σ = 0.03).
  - `is_fraud` = rating ≥ 0.6.
- The rating weights are prototype choices, tuned so the documented demo scenarios land in their bands. When a scenario lands in the wrong band, the fix is to change the data or the weights and retrain. Scores are never hard-coded.
- Split: time-based 70 / 15 / 15 (train / validation / test).

## Features

| Component | Features |
|---|---|
| Amount | `log_amount`, `amount_ratio` (to the 30-day average), `amount_z`, `share_of_balance`, `is_round` |
| Behaviour | `is_new_recipient`, `prior_count`, `tx_count_30m`, `value_24h_ratio`, `indirect_connection`, `is_p2m` |
| Context | `is_night`, `hour_deviation` (circular mean of past payment hours), `new_device`, `account_age_days` |

Non-learned inputs to the stacker:

- `graph`: the payment-chain score, `[0, .2, .5, .8][hops] × (0.6 + 0.4 × average similarity)`, with at most 3 hops.
- `receiver`: 1.0 for a watchlisted account; otherwise an additive score from unregistered ID, new account, many payers and pass-through outflow.

## Training setup

- Each component: `binary:logistic`, 60 trees, max depth 3, eta 0.2, lambda 1, gamma 0, subsample 0.8, `hist` with 32 bins, `scale_pos_weight = min(4, negatives / positives)`, seed 42.
- Stacker: ordinary least squares on the validation slice. Inputs are `[p_amount, p_behavior, p_context, graph, receiver]` and the target is the synthetic analyst rating. The output is clipped to [0, 1] and multiplied by 100.
- Export check: the browser-format trees are compared with xgboost's own predictions on the test slice. Training stops if any difference exceeds 1e-4. The browser compares in float32, like xgboost.

## Evaluation (synthetic test slice, 3,600 rows)

| Metric | Value |
|---|---|
| Precision (score ≥ 60 vs rating ≥ 0.6) | 0.922 |
| Recall | 0.891 |
| F1 | 0.907 |
| PR-AUC | 0.976 |
| Confusion matrix | TP 475, FP 40, FN 58, TN 3,027 |
| Component PR-AUC | amount 0.977, behaviour 0.767, context 0.626 |
| Stacker R² | validation 0.942, test 0.941 |

The behaviour and context components score lower on PR-AUC because their labels are Bernoulli draws from moderate severities. Recovering them perfectly is impossible by design. **None of these numbers transfer to real data.**

## Ethical considerations and limitations

- **Synthetic bias:** the model reflects the generator's assumptions. For example, it treats a new recipient as moderately unusual and night-time payments as unusual. Real behaviour varies across people, regions and professions, and a real system would need fairness testing.
- **Explanations:**
  - Reason codes come from feature conditions and component outputs, not from causal analysis.
  - User-facing text never shows raw thresholds or weights.
- **Privacy:**
  - Receiver information is reduced to a level and a generic note.
  - Only the direct payer in a chain is named.
- **Graph signals:** a payment chain or indirect connection is only a pattern. It can come from ordinary life, such as splitting a bill or repaying someone.
- **Thresholds:** 30, 60 and 85 are Yogii prototype values, not RBI, NPCI or bank standards.
- **Failure mode:** if the model is missing or doesn't match the app's feature lists, the app refuses to score. It never falls back to rules.

## Reproducibility

```bash
python ml/train.py            # byte-identical artifact for the same engine and seed
python ml/check_scenarios.py  # checks every demo scenario band
```
